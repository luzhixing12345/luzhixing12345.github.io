# CubeSandbox 存储篇

这是 CubeSandbox 系列的第二篇。[架构篇](/blog/cubesandbox-architecture/)说过，这套系统的核心思路是“冷启动在模板阶段付一次，运行时只做本机克隆和快照恢复”。这个思路能不能落地，关键在存储：创建一台沙箱时，磁盘和内存镜像都不能真的拷一份。

CubeSandbox 的做法是把所有大文件都放在本地 XFS 上，用一次 `FICLONE` ioctl 完成克隆。本篇讲沙箱的盘怎么拼起来、模板怎么来、reflink 在文件系统里做了什么、CubeCoW 在 reflink 之上加了哪些规矩，以及跨节点和数据卷这两条旁路。内存快照里的页面筛选逻辑放在[虚拟化篇](/blog/cubesandbox-virtualization/)，网络放在[网络篇](/blog/cubesandbox-network/)。

## 一台沙箱的盘长什么样

```demo
demos/cube-disk.html
```

一台沙箱的存储由五样东西拼成，分成三类。

**只读、全机共享的**：客户机操作系统镜像、guest agent 镜像，以及模板对应的 OCI 镜像。三者都是 ext4 镜像文件，用 virtio-pmem 交给虚拟机，并标记 `discard_writes`，客户机写不回宿主机。客户机里以 DAX 方式挂载：读文件时直接访问宿主机页缓存里的那一页，不在客户机里再缓存一份。一台机器上跑几百台同模板的沙箱，这些只读内容在物理内存里也只有一份。

**每台沙箱私有、可写的**：一个由 CubeCoW 管理的 ext4 文件，名字形如 `sb-<沙箱ID>-rootfs-gen0`，用 virtio-blk 交给虚拟机。它是从模板的可写层 reflink 克隆来的，格式化时关掉了 ext4 的日志。

**穿透到宿主机的**：用户声明的宿主机目录或数据卷，先 bind 到 `/data/cubelet/hostdir/<沙箱ID>/` 下，再经 virtio-fs 共享进去。

客户机里，agent 把容器的根文件系统组装成一个 overlayfs：下层是只读的模板镜像，上层和工作目录放在可写盘里的 `disk/<容器ID>` 下。读文件先走模板镜像，写入只落在可写层。

这样拆开有一个直接后果：**创建一台沙箱，真正新增的只有那个可写层文件，而它是一次 reflink 克隆出来的。**模板镜像、系统镜像、agent 镜像都是已经在盘上的共享文件，直接挂上就行。

## 模板从哪里来

```demo
demos/cube-tpl.html
```

模板的构建分两段。

第一段在控制面，只做一次。TemplateCenter 拉取 OCI 镜像、解包出根文件系统，用 `mkfs.ext4 -d` 把整个目录直接打成一个 ext4 镜像，上传到制品存储（S3、MinIO 或本地目录）。镜像格式是 ext4，不是 erofs；开源版本里 erofs 镜像卷的代码路径会直接报“不支持”。

第二段在每台计算节点上各做一次。CubeMaster 选好节点，用 gRPC 下发模板副本。节点把 ext4 镜像下载到本地，按制品 ID 缓存。然后它用 CubeCoW 新建一个空的构建可写层 `tpl-<模板ID>-build-rootfs` 并格式化，冷启动一台临时虚拟机，跑镜像的入口命令，等配置好的 HTTP 探针返回 2xx。

探针一通，节点就把虚拟机冻结，做两件事：把整份客户机内存写成 `tpl-<模板ID>-memory`，把构建可写层 reflink 一份成 `tpl-<模板ID>-rootfs`。之后构建用的可写层就可以删了。这份模板快照里，服务已经启动完毕、正在监听端口。由它创建出来的沙箱，在创建调用返回时，被探测的那个端口已经能接请求。

探针选得不好会出问题：返回得太早，快照里的服务可能还在初始化；一直不成功，构建会超时。只暴露、没被探测的端口，没有这层保证。

部署约束也由此而来。模板要在每台节点的本地盘上各存一份，所以每台节点都需要足够的本地盘；创建依赖 reflink，所以 `/data/cubelet` 必须是打开 reflink 的 XFS。

## reflink 在 XFS 里做了什么

```demo
demos/cube-reflink.html
```

XFS 用每个 inode 里的一棵 B+ 树（BMBT）记录“文件的第几块对应磁盘上哪个物理块”，每条记录是一段连续区间，叫 extent。打开 reflink 后，文件系统另外维护一棵全局的引用计数树，记录每个物理块被几个文件引用。

`ioctl(dst, FICLONE, src)` 做的事很简单：把 src 的 extent 映射复制给 dst，再把这些物理块的引用计数各加一。全程只改元数据，不读也不写数据块，耗时和文件里有多少数据基本无关。

之后谁往一个共享块里写，XFS 就新分配一个物理块，把写入落在新块上，并把写入者的映射改指过去；旧块的引用计数减一，降回 1 时它又变成独占块，下次写入不必再分裂。另一个文件的映射和数据完全不受影响。这就是写时复制，粒度是文件系统块，而不是整个文件。

对沙箱来说，这意味着：从模板克隆可写层是一次元数据操作；沙箱运行时写到哪一块，才为哪一块付出复制的代价；几百台沙箱共享模板里没被改过的那些块。

## CubeCoW：在 reflink 上加规矩

裸 reflink 只解决了“快”，没解决“管”：卷怎么命名、快照放哪、崩溃后怎么知道哪些文件是半成品。CubeCoW 是专门干这件事的 Rust 库。

它不是一个独立服务。CubeCoW 编译成带 C ABI 的动态库，Cubelet 通过 cgo 把它链进自己的进程，每个后端初始化一个句柄。reflink 后端的根目录由 Cubelet 固定在 `/data/cubelet/storage/xfs/objects`，每个卷是 `volumes/<卷名>/<卷名>` 这样一个普通文件，同卷的快照放在同一个目录下。新建卷只是 `set_len` 出一个稀疏文件，不预分配空间。

在此之上，它定了三条规矩。

**快照是扁平的。**

```demo
demos/cube-flat.html
```

reflink 本身允许给快照再拍快照。CubeCoW 让每个快照的 `origin_volume` 都记为最终的祖先卷，文件也放在祖先卷的目录下。从文件系统看，主卷和它所有的快照都是同一目录里平级的普通文件，各自拥有完整的 extent 映射。删除中间某一份就是 `unlink` 一个文件，物理块的引用计数由 XFS 去减，其他快照不用跟着改。血缘关系只记在内存索引里，用来回答“这份快照是从哪来的”。

为了配合模板构建，删除卷时如果目录里还有快照，CubeCoW 只删主文件、保留目录；最后一个快照删掉时目录跟着回收。这正是“提交模板后删除构建可写层”需要的语义。

**磁盘本身就是账本。**卷的列表等于列一遍 `volumes/`，快照的列表等于列卷目录再去掉主文件，大小和时间来自 `stat`。CubeCoW 不另写一份元数据文件。引擎启动时扫一遍目录重建内存索引，并按几条规则清理崩溃残留：

| 磁盘上看到的 | 怎么处理 |
| --- | --- |
| 卷目录里有主文件 | 登记为卷 |
| 目录为空 | 删掉孤儿目录 |
| 主文件没了，还有快照文件 | 只恢复快照，打警告 |
| 零字节的快照文件 | 删掉，那是 `FICLONE` 没做完就崩了 |
| 重名 | 跳过并警告 |

一次快照落到磁盘上只有两步：一次 `FICLONE`，一次目录 `fsync`。中途失败就回滚索引、删掉半成品。没有独立账本，就不存在账本和磁盘对不上的问题。

**卷和快照共用一个命名空间。**内存里是一张受读写锁保护的表，卷名和快照名在同一个空间里。新建任何对象都在写锁下先占名再做 `FICLONE`，并发创建不会撞名，也不用沿血缘递归查重。

启动时还有一道检查：CubeCoW 会在根目录里建个小文件真的做一次 `FICLONE`，失败就拒绝启动。这比运行到一半才发现文件系统不支持要好得多。

## 创建、快照、回滚、克隆在盘上各做了什么

有了上面这些，几种操作在存储层面都很直接。

- **创建**：从 `tpl-<模板ID>-rootfs` reflink 出 `sb-<沙箱ID>-rootfs-gen0`。内存镜像不用克隆，虚拟机以只读的私有映射直接打开模板的内存文件，写入只发生在进程自己的内存里。
- **快照**：冻结客户机，把当前可写层 reflink 一份，再写一份内存镜像。内存镜像同样先 reflink 上一份作为基线，然后只覆盖改过的页，这样写出来的仍是一份完整布局的镜像。具体覆盖哪些页，见[虚拟化篇](/blog/cubesandbox-virtualization/)。
- **回滚**：CubeCoW 没有专门的回滚接口。Cubelet 从目标快照派生一份新一代的可写层（文件名里的 `gen` 加一），再从目标内存快照恢复虚拟机。
- **克隆**：先给源沙箱拍一份临时快照，再从它创建 N 台，最后尽力删掉临时快照。N 台的可写层共享同一批 extent，内存镜像也共享同一份页缓存，谁先写谁分裂。任何一台创建失败，已经建出来的会被销毁，调用方要么拿到 N 台，要么拿到异常。

## 跨节点：S3 后端和 CubeS3lvol

reflink 是本机文件系统的能力，克隆出来的文件和源文件必须在同一个 XFS 上。0.7.0 加了一个 S3 后端，让暂停的沙箱可以在另一台节点上恢复。

S3 后端背后是一个独立进程 CubeS3lvol。它基于 SPDK，把一个卷的数据放在对象存储里，本地盘只放预写日志、元数据日志和数据块缓存，然后以 NVMe/TCP 的形式在本机回环导出，宿主机上看到的是一块普通的 `/dev/nvmeXnY`。写入先落本地日志再异步上传，崩溃后靠本地日志恢复。快照、克隆、导出、导入都是它的 RPC。

CubeCoW 的 S3 后端通过 Unix socket 调这些 RPC，和 reflink 后端实现同一套接口。有一处不同：S3 后端在本地维护一个 `index.json`，记录名字、激活状态和导出 ID，因为“文件就是账本”在对象存储上不成立。

跨节点暂停时，Cubelet 把可写层快照、内存卷和元数据卷封存后导出到 S3；在另一台节点恢复时，先导入成本地卷，再走正常的恢复流程。即使在同一台节点上恢复，S3 后端也要把内存克隆成一份沙箱私有的盘，因为暂停包对应的 NVMe 设备随时可能被摘掉，虚拟机不能直接映射它。reflink 后端则没有上传这一步，暂停包始终留在本机盘上。

模板的后端在创建时就定下，整条血缘都跟着它。毫秒级的创建仍然只走本地 reflink；S3 解决的是“状态跨过单机磁盘”。这项能力目前标为预览，默认搭配内置的 MinIO。

## 数据卷和宿主机目录

上面讲的都是虚拟机根文件系统和内存，生命周期跟着沙箱走。用户数据另有两条通道，都和 CubeS3lvol 无关。

- **宿主机目录挂载**：把宿主机上的一个目录 bind 到 `/data/cubelet/hostdir/<沙箱ID>/` 下，再经 virtio-fs 共享进客户机。这种挂载绑定节点，跨节点恢复时只能回到原节点。
- **Volume 插件**（0.6.0）：生命周期独立于沙箱，可以挂到不同沙箱上。插件实现控制面的创建/删除钩子和节点上的挂载/卸载钩子，仓库里有 s3fs、COS、JuiceFS 的示例。插件把存储挂到宿主机后返回一个路径，Cubelet 复用宿主机目录那套 bind 加 virtio-fs 的机制把它送进客户机。

## 和文档对照时要注意的几处

- CubeCoW 的 README 还写着只有 reflink 一个后端，源码里 S3 后端已经接入 Cubelet。
- 它的 API 文档暗示有快照时删不掉卷；reflink 实现已经允许只删主文件、保留快照。
- 一些文档把 reflink 根目录写成 `/var/lib/cubecow/reflink`，生产部署由 Cubelet 固定在 `/data/cubelet/storage/xfs/objects`。
- XFS 后端把沙箱的可写层登记成“快照”类型的对象，这只是 CubeCoW 内部的对象种类，不代表它在客户机里是只读的。
